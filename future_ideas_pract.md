# Практическая часть: структурный prior для голов и адаптеров

Дата: 2026-09-06.

Сводка обсуждения практического продолжения проекта. Текущие синтетические эксперименты рассматриваются как основа теоретической статьи; описанные здесь практические варианты пока являются предложениями, а не полученными результатами.

Связанный документ: [идеи для теоретических экспериментов](future_ideas.md).

## Основная постановка

**По решениям предыдущих задач обучить prior, который помогает адаптировать модель к новой задаче на небольшом количестве данных.**

Сохранить основной механизм текущего pipeline:

```text
Банк успешных сетей
    → извлечение общей структуры
    → обучение prior
    → перенос структуры на новую задачу
    → обучение и проверка новой модели
```

Обучение генератора через downstream loss добавить отдельным вариантом. Это позволит отделить пользу информации, извлечённой из банка, от пользы дополнительного meta-training.

В синтетике структура сравнивается с известной ideal-маской. В практической части полезный inductive bias может выражаться через:

- совместный выбор признаков;
- повторяющиеся группы связей, полезные для семейства задач;
- небольшое пространство параметров, в котором достаточно выполнять адаптацию.

Необязательно находить узнаваемую свёртку. Проверяемый тезис: общая структура успешных решений сокращает количество данных, необходимых для обучения следующей задачи.

## Первый вариант: выходные классификационные головы

Начать с одного замороженного encoder и небольшой головы:

```text
x → frozen encoder φ(x) → masked bottleneck → классификатор задачи
```

VAE/CVAE генерирует маску bottleneck-слоя. Его веса и последний классификатор обучаются заново на новой задаче. Это прямой перенос текущей схемы: генерируется структура, а не готовая функция классификации.

Почему такой вариант удобен:

1. **Общее пространство признаков.** Все исходные и целевые головы используют один checkpoint encoder. Независимое дообучение всего backbone смешало бы различия голов с различиями входных представлений.
2. **Выходные классы остаются специфичными для задачи.** Одинаковый номер класса в MNIST и Fashion-MNIST не означает одинаковую семантику. Строки последнего слоя нельзя напрямую усреднять без определения соответствия.
3. **Одинаковая форма генерируемого объекта.** Bottleneck может сохранять размер при разном количестве выходных классов.

Перестановки скрытых нейронов bottleneck всё ещё надо учитывать. Более простой начальный контроль — генерировать вектор выбора признаков перед линейной головой: он не добавляет скрытый слой с перестановочной неоднозначностью.

Первым объектом генерации выбрать **маски или gates**. Перенос готовых весов головы, их инициализации или поправок к ним проверять отдельно: это другой механизм, и его выигрыш нельзя приписывать только структуре.

## Датасеты и выбор backbone

MNIST/Fashion-MNIST подходят для дешёвого переходного эксперимента. Для изображений естественнее CNN или [ViT](https://arxiv.org/abs/2010.11929). [BERT](https://arxiv.org/abs/1810.04805) предобучен для текста; если интерес именно к нему, основной эксперимент лучше строить на текстовых задачах.

**Тысяча голов на двух задачах — всё ещё только две задачи.** Seeds дают разнообразие решений, но не заменяют разнообразие задач для проверки переноса prior.

Предлагаются два этапа:

| Этап | Постановка | Что проверяет |
|---|---|---|
| Дешёвый пилот | Визуальный encoder; задачи классификации подмножеств классов MNIST/Fashion-MNIST | Работоспособность переноса структуры; отдельно перенос на отложенные классы или датасет |
| Основной практический эксперимент | BERT; семейство задач классификации интентов, например эпизоды на [CLINC150](https://aclanthology.org/D19-1131/) | Few-shot перенос на заранее отложенные классы или домены |

Заранее разделить исходные примеры и целые задачи. Новые эпизоды из тех же классов, новые классы и новый домен — разные уровни переноса, которые надо оценивать отдельно.

Различать две постановки:

- **Multitask на известных задачах:** все задачи доступны при обучении; проверяется полезность совместного обучения и обмена информацией.
- **Перенос на новую задачу:** prior обучен на meta-train задачах, затем заморожен; новая задача доступна только через ограниченный support-набор.

Обе постановки осмысленны. Вторая теснее связывает практическую часть с гипотезой о переносимом inductive bias.

## Предлагаемое изменение pipeline

1. **Банк голов.** Обучить небольшие головы для множества meta-train задач поверх одного frozen encoder. Использовать несколько инициализаций на задачу; отбирать кандидатов по отдельной validation-части этой задачи.
2. **Структурные объекты.** Извлечь маски, importance-карты или gates. Проверить повторяемость сигнала между задачами и сравнить с простым усреднением до усложнения генератора.
3. **Общий prior.** Начать с unconditional VAE. Для CVAE отдельно определить доступное описание задачи и проверить, помогает ли conditioning.
4. **Перенос.** На held-out задаче сгенерировать структуру и обучить свежую голову на ограниченном support-наборе. Финальное качество измерить на query, который не используется для выбора маски или адаптации.
5. **Отдельный вариант с meta-finetuning.** Дообучить генератор через query-loss после адаптации головы на support внутри meta-train. Сопоставить результат с генератором, обученным только на банке.

Для масок использовать одинаковое число активных связей и проверять результат после hard-бинаризации. Если проводится поиск latent на support целевой задачи, учитывать его стоимость и описывать как отдельный адаптационный режим. Query не должен участвовать в выборе latent или лучшего сэмпла.

## Откуда брать condition новой задачи

One-hot ID известных задач не задаёт содержательного представления новой задачи.

Возможный вариант — статистики support-примеров в пространстве encoder, включая информацию о классах. Описание задачи должно корректно учитывать произвольную нумерацию классов и вычисляться только из данных, доступных при адаптации.

Если для condition сначала приходится полностью обучить хорошую голову новой задачи, преимущество по стоимости адаптации может исчезнуть. Поэтому генерация из support-описания, адаптация latent и реконструкция уже обученной головы — разные режимы, которые следует разделять.

## Что переносим из последних синтетических результатов

- В [motif OOD](motif_pair/OOD_RESULTS.md) conditional mean не уступает CVAE в основном seen-gap результате. Необходимость стохастического latent пока не установлена.
- В [финальном исследовательском отчёте](mds/FINAL_REPORT_2026-09-08.md) показано, что более точная reconstruction конкретной importance-карты не означает более близкую к ideal бинарную структуру. Хорошая reconstruction банка не гарантирует переноса; неудача конечного oracle-поиска также не доказывает глобальную недостижимость unseen ideal.

Эти результаты мотивируют практический эксперимент, но сами по себе не доказывают перенос на естественные данные.

## Следующий масштаб: внутренние матрицы

После эксперимента с головами перейти к небольшим поправкам к замороженным весам:

```text
W_(task, layer) = W_(base, layer) + ΔW_(task, layer)
```

Объектом prior могут быть adapters или низкоранговые обновления в духе [LoRA](https://arxiv.org/abs/2106.09685). Генератор может выдавать коэффициенты общего набора обновлений, получая описание задачи и слоя.

Это позволяет адаптировать внутренние представления, сохраняя умеренный размер генерируемого объекта. Начинать с генерации полных внутренних матриц BERT менее удобно: выше размерность и сложнее отделить структурный перенос от переноса конкретных весов.

Прямой ориентир — [HyperFormer](https://aclanthology.org/2021.acl-long.47/), который генерирует task-specific adapters общей hypernetwork. Поэтому гипотеза для этого этапа должна быть конкретной: prior из множества успешных решений даёт дополнительную пользу, а стохастический CVAE превосходит сопоставимый детерминированный генератор. Сам факт генерации адаптеров не является новым результатом.

## Сравнения и метрики

Для первого эксперимента с головами:

| Метод | Назначение |
|---|---|
| Обычная голова без learned prior | Практический baseline адаптации |
| Random-маска того же размера | Контроль числа связей и ограничения ёмкости |
| Простой общий prior, например средняя importance-карта | Проверка необходимости сложного генератора |
| Детерминированный условный генератор | Проверка необходимости стохастического latent |
| VAE/CVAE | Проверяемый генеративный prior |

Для multitask-постановки добавить стандартное совместное обучение с отдельными головами. Для внутренних обновлений — независимо обучаемые adapters/LoRA и детерминированную hypernetwork.

Все методы сравнивать с одинаковым encoder, объёмом target-данных и сопоставимым бюджетом адаптации. Настройки выбирать внутри meta-train/meta-validation, не по финальным held-out задачам.

Основной график — **качество на новой задаче против числа размеченных примеров**, например 5, 10 и 20 на класс. Дополнительно измерять:

- разброс и отрицательный перенос по задачам;
- время и число обучаемых параметров при адаптации;
- отдельную стоимость банка и обучения prior;
- при использовании нескольких сэмплов — их вычислительную стоимость и правило агрегации/выбора.

## Позиционирование практической части

[The Deep Weight Prior](https://arxiv.org/abs/1810.06943) уже использует генеративную модель обученных CNN-фильтров как prior для новых моделей. [HyperFormer](https://aclanthology.org/2021.acl-long.47/) уже переносит информацию между задачами через генерацию адаптеров.

Потенциальный вклад проекта стоит связывать со способом извлечения структуры из успешных решений, условиями её переноса и преимуществом над простыми priors. Основной проверяемый вопрос:

**Помогает ли обнаруженная в предыдущих решениях структура обучаться на новых задачах с меньшим количеством данных, и что сверх этого даёт CVAE?**
